# zhdata：独立进程 vs 合并进 s-ui（评估 · 2026-11-24）

背景：C455 上线 ZY9 时踩到「界面把入站端口改成 45501-45564，但 zhdata 进程还听 49888-49919，客户端连不上」。
这暴露的是**跨进程架构**的运维成本。问题是：既然如此，有没有必要把 zhdata 核心拆成 Go 包直接跑在 s-ui 进程里？

## 0. 结论（先给答案）

**保留独立进程**，但把「进程怎么起」这件事彻底交给面板（ZY10 已实现）。
合并的唯一**硬**收益是「同一进程内的统一限速与统一计费」。如果那是产品硬需求，走合并（路线 B）；
否则 B 的代价（面板重启语义、升级节奏、崩溃半径）明显大于它解决的运维麻烦。

判定标准一句话：**会不会出现「同一个客户在同一节点上同时走 zhdata 和其它入站，且必须共享一份带宽」**。
会 → 需要 B 或「共享令牌桶服务」（§4 步 2）；不会 → A 就够，缺的只是可观测性。

## 1. 这两天实际暴露的问题，按性质分类

| # | 现象 | 性质 | 处置 |
|---|---|---|---|

## 2. 两种形态的硬事实

| 维度 | A：独立进程（现状 + ZY10 托管） | B：核心内嵌进 s-ui 进程 |
|---|---|---|
| 数据面隔离 | **面板重启/升级不断隧道**。今天 C455 面板重启两次、换二进制两次，zhdata 隧道全程没断 | 面板每次 config 重建/重启都会带走全部 zhdata 隧道（s-ui 在多条保存路径上会 full restart box） |
| 升级节奏 | 核心＝换一个文件 + restart（秒级，不碰面板）；zhenhanvn 客户端走同一条 GitHub release 自动升级 | 核心任何改动都要重编译整个面板（WSL cgo + migration + 面板重启），每次核心修 bug 都要 bump 一个 ZYn |
| 版本偏斜 | 有，靠契约字段协商（旧核心忽略新字段、旧面板不发字段） | 无（同一二进制） |
| 限速/计费 | 两套桶：hy2（面板进程 `bwlimit.Wrap`）+ zhdata（核心进程令牌桶）⇒ 一个客户名义 2M 实际可 2×2M；stats 按 tag 快照 ⇒ 重复入站会双计 | **一套桶**：跨协议真正 per-user 限速，顺带消掉 stats 双计与 ≤60s 不限速窗口 |
| 崩溃半径 | 核心崩了面板仍在（还能看到告警、能点重启）；面板崩了隧道仍在跑 | 一崩全崩（UI、订阅、其它 sing-box 入站一起） |
| 内存（971MB 机器） | 多一份进程 RSS（zhdata 在这个量级约 20-40MB） | 省一份，但面板 RSS 同步上涨 |
| 客户端形态 | 与 A/B 无关：zhenhanvn 需要一个独立的 zhdata 可执行文件 ⇒ **库边界无论如何都得存在** | 同上，B 只是换宿主进程 |
| 现有代码规模 | 核心：19 个非测试文件 **8,078 行**（+4,938 行测试）。面板侧「跨进程胶水」≈**1,600 行**（`service/zhdata.go` 1,063、`service/zhdata_unit.go` 307、`cronjob/zhdataStatsJob.go` 28、`util/zhdata.go` 53） | 能删掉大部分胶水，但要新增 inbound 适配 + 生命周期解耦（见 §3） |
| 技术可行性 | — | 可行：核心已导出 `NewServer(ServerOptions)`（`zhdata-src/api.go:115`）；s-ui 自 ZY6 起就在面板进程里用 `zhdatacore.NewClientApp` 做 zhdata 出站（`core/protocol/zhdata/outbound.go`），`go.mod` 已 `replace … => ../v2rayn/zhdata-src` |

## 3. B 的真实成本（不是「把 NewServer 塞进 AddInbound」那么小）

1. **生命周期要解耦**：s-ui 保存客户/入站会重建 box；zhdata 的会话表、按 uuid 的令牌桶、slot 状态必须跨重建存活。
   做法是把 Server 做成进程级 singleton（面板启动时创建，只有 `-listen/backend/max_sessions/decoy` 真变了才 Close/New），
   也就是把 ZY10 里「ExecStart 变了才 restart」的判断，从 systemd 层搬到进程内层。
2. **它就不再是 sing-box inbound**：zhdata 需要自己的 listener 与用户源，等价于「A 的进程内版本」，
   仍然是一个 zhdata server 实例，只是宿主换了 —— 所以 B 并不会消灭「一个 server 实例 + 一堆配置」这个概念，
   只是消灭了进程边界。
3. **重启语义必须改**：否则一次「保存面板设置」会把全站隧道打断（现在不会）。这是 B 最容易被客户感知的回归。
4. **观测面变化**：核心日志混进 s-ui journal（要 tag）；`systemctl restart zhdata` 这类应急手段消失。
5. **迁移工作量**：4 台节点的 `zhdata.service` / C498 的 `zhdata-relay.service` 退场，relay 变成面板里的入站配置；
   面板 upgrade 变成「隧道会断」的事件，需要发布窗口。

## 4. 建议路线（不必现在二选一）

1. **现在（A 强化，已完成/待补）**
   - 已做：面板生成/更新 systemd unit（ZY10）、核心 `-init-view`、契约文档 §2.4 部署顺序。
   - 待补（都很小）：`GET /v1/stats` 回显实际监听端口 + 面板比对 `listen_ports` 标红；
     入站保存时 `admin_addr` 与既有 zhdata 入站重复 ⇒ 明确警告（说明 relay 会互相覆盖、流量会双计）。
2. **若「跨协议统一限速」变成硬需求**（同一个客户同时走 hy2 与 zhdata）：
   先别整体合并，做 **P1 共享令牌桶服务**——本机一个 unix socket 的小授权进程，两个数据面都向它取令牌。
   保住 A 的进程隔离，拿到 B 的统一限速（这也是 P1 跨进程设备数租约的同一条路子）。
3. **B 只在一种形态下划算**：面板就是节点上唯一的进程、且能接受「保存即断隧道」的单体发行版形态。
   以现在「面板常升级、核心要热换、zhenhanvn 客户端独立升级核心」的运维方式，B 不划算。

## 5. 一句话带走

今天的问题不是「核心是独立进程」，而是「独立进程的启动参数没人托管」——这个已经在 ZY10 里补上了；
真正需要架构决策的只有「跨协议共享带宽」，而那件事有比重复造一个单体更便宜的解法（共享令牌桶）。
